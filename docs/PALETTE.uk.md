# Палітра Power Dolls 2 (PC-98)

## ⚠️ Читати першим: дефолтна шкала — не палітра художніх екранів

`pd2extract.py` рендерить **дефолтною палітрою PC-98**, якщо не передати `--pal`
або `--pal-exe` — тією шкалою, що запакована в 24 з 26 файлів `.GCP`. Шкала
справжня, але це **не та палітра, яку гра ставить на екран для своєї графіки**.
Тому `--all` без параметрів пише PNG із неправильними кольорами, і це дуже легко
цілий день списувати на кодек.

![ті самі пікселі з трьома палітрами](img/palette_default_vs_screen.png)

*Той самий кадр (`FACE.PCK`, запис 0) і три палітри. Ліворуч — дефолтна.
Посередині — таблиця, яку справді використовують екрани спорядження/художні.
Праворуч — інша справжня таблиця гри (геймплей): теж виглядає «схоже», але це не
таблиця цього екрана.*

*Панелі відтворюються так: `python pd2extract.py --pck FACE.PCK out\x --pal-exe
BRIEFING.EXE:0x234C6`, той самий прогін із `--palette pc98` і з
`--pal-exe TACTICS.EXE:0x1ECA4`.*

Дефолтна має з кожною з чотирьох палітр екранів, що лежать в EXE і підтверджені
живими дампами з емулятора, не більш ніж **2 спільні кольори з 16** (чорний і
білий), а по позиціях збігається лише один запис — нульовий:

| палітра екрана | записів, що дорівнюють дефолтній |
|---|---|
| `STARTUP.EXE` `0x9311` (запуск) | 1/16 |
| `PD2SHELL.EXE` `0x98E6` (оболонка/меню) | 1/16 |
| `BRIEFING.EXE` `0x234C6` (спорядження/художні) | 1/16 |
| `TACTICS.EXE` `0x1ECA4` (бій/тактика) | 2/16 |

Піксельні дані тут ні до чого: геометрія дефолтного рендера точна, а
`tools/verify.py` проходить на всіх 360 зображеннях. Проблема лише в
16-кольоровій шкалі.

### Як отримати кольори як у грі

Палітра лежить не поруч із пікселями. Більшість записів-картинок не несуть
палітри взагалі — у `FACE.PCK` запакованої таблиці немає в жодному з 38 записів;
ті небагато архівів, що справді мають 32-байтову таблицю за зсувом `0xB` (напр.
`CHARA.PCK`, §2 нижче), несуть **дефолтну** шкалу, а не палітру графіки. Потрібна
ж таблиця — це 48 байтів в EXE, порядок каналів **B,R,G**, і передається вона
витягувачу опцією `--pal-exe`:

| що витягуєте | що передати |
|---|---|
| портрети / художні екрани / спорядження (`FACE.PCK`, …) | `--pal-exe BRIEFING.EXE:0x234C6` — та сама таблиця також у `CONVERT.EXE` `0xF9D0`, `OPENING.EXE` `0xCF0E`, `REPORT.EXE` `0x13E5C`/`0x169A2`, `TACTICS.EXE` `0x2290E` |
| бій / тактика (геймплей) | `--pal-exe TACTICS.EXE:0x1ECA4` |
| оболонка / меню | `--pal-exe PD2SHELL.EXE:0x98E6` |
| екран запуску | `--pal-exe STARTUP.EXE:0x9311` |
| перегляд вбудованої шкали в `HARDY.GCP` / `KOGADO.GCP` | `python pd2pal.py --gcp HARDY.GCP -o out\hardy.pal` витягує 32-байтову палітру; `.GCP` — це display-list, який рендерить `pd2gcp.py`, а не `pd2extract.py` |

```powershell
# палітра художніх екранів, перевірена на екрані спорядження
python pd2extract.py --pck ..\hdi\PD2D\FACE.PCK out\face --pal-exe ..\hdi\PD2D\BRIEFING.EXE:0x234C6

# усі таблиці під текою даних, як .pal (44 для PD2D; 127 по shipped HDI+FDI)
python tools\pal_tables.py --dump out\pal\tables --data ..\hdi\PD2D
python pd2extract.py --all ..\hdi\PD2D out\png --pal out\pal\tables\TACTICS.EXE_01eca4.pal

# екран, який ще не зіставлено: зніміть його в DOSBox-X (Ctrl+F5 -> .png + .pal)
python pd2extract.py --all ..\hdi\PD2D out\png --pal capture\game.pal
# ... або спитайте, з якої таблиці цей знімок, і використайте --pal-exe
python tools\pal_tables.py --find capture\game_analog.rgb --data ..\hdi\PD2D
```

Три речі, які варто тримати в голові:

* **Зіставлення йде за екраном, а не за файлом.** Живим дампом зіставлено лише
  чотири екрани вище; гра постачає **59 різних палітр**, і решта ще не
  прив'язана до екранів ([`PALETTE_TABLES.md`](PALETTE_TABLES.uk.md) §6). Якщо
  невідомо, до якого екрана належить архів, — зніміть цей екран; це єдиний
  надійний спосіб дізнатися, **яку** таблицю брати.
* **Живий знімок зазвичай приглушений.** Гра фейдить палітри в рантаймі драбиною
  `k/16`, тому `pal_tables.py --find` зазвичай показує джерело як `15/16`. Беріть
  збережену таблицю (повна яскравість), а не приглушений знімок.
* **`--palette gray` / `vivid` — це не результат по кольорах.** Це режими для
  геометрії/налагодження: `gray` — щоб бачити структуру, `vivid` — навмисно
  фальшива контрастна шкала.

## 1. Механізм — доведено дизасемблером

Рутин запису палітри: **`CONVERT.EXE` образ `0x5F87`** (той самий код у
кожному графічному EXE; у `BRIEFING.EXE` це образ `0x10A69`).

```c
/* аргументи: struct (far), x, y, flag */
if (struct[8] >= 0x22 && flag != 0) {
    for (i = 0; i < 16; i++) {
        b0 = es:[bx + 0x0C];        /* bx = указівник на struct + i*2 */
        b1 = es:[bx + 0x0B];
        out(0xA8, b0 >> 4);         /* ІНДЕКС палітри */
        out(0xAA, b0 & 15);         /* ЗЕЛЕНИЙ */
        out(0xAC, b1 >> 4);         /* ЧЕРВОНИЙ */
        out(0xAE, b1 & 15);         /* СИНІЙ */
    }
}
```

`0xA8` отримує індекс — старший нібл першого байта завжди дорівнює номеру
запису `i` — але три кольорові порти це **`0xAA` = зелений, `0xAC` = червоний,
`0xAE` = синій**. Це розводка PC-98, а не припущення: DOSBox-X
(`src/hardware/vga_pc98_gdc.cpp`) на запис у `0xAA` встановлює `dac.rgb[].green`
і `pc98_pal_analog[+0]`, на `0xAC` — `.red` / `[+1]`, на `0xAE` — `.blue` /
`[+2]`, а сам масив оголошено як `/* G R B */`.

Остаточно це закриває власна шкала гри — таблиця в 24 з 26 файлів `.GCP`.
З наведеними портами вона декодується як

```
000 00f f00 f0f 0f0 0ff ff0 fff   777 00a a00 a0a 0a0 0aa aa0 aaa
```

тобто рівно як апаратна шкала скидання PC-98 (`G = i&4`, `R = i&2`, `B = i&1`:
1 = синій, 2 = червоний, 3 = маджента, 4 = зелений). Читання ніблів у
зворотному порядку дає 2 = зелений і 4 = червоний — такої шкали не має жодна
PC-98. Та сама помилка перетворює packed-палітри «малюнків» зі збірки Advanced
PD2 на зеленовані версії відомої 48-байтової таблиці `BRIEFING.EXE 0x234C6` —
саме так її й було виявлено: рендер тих блоків у неправильному порядку дає
зелену шкіру.

![той самий фінальний екран Advanced PD2, прочитаний неправильно (ліворуч) і правильно (праворуч)](img/palette_order_fix.png)

Ця пара — вся помилка в одному зображенні: лівий кадр — це те, як виглядали
фінальні екрани з `M_CLR1.PCK` і `AD_END.PCK`, поки порядок був неправильний
(зелена шкіра, зелений фон), а виправлення — це лише два нібли, прочитані
навпаки. `palette_to_packed(palette_from_packed(x)) == x` байт-у-байт на всіх 26
файлах `.GCP` — це запобіжник від регресії (перевірка `[5]` у
`tools/verify.py`).

### 48-байтові таблиці: порядок байтів залежить від гри

Банки всередині EXE — по 48 байтів, 3 на запис, але дві ігри зберігають канали в
різному порядку, і визначити це можуть лише палітри, зняті з живої гри:

| гра | EXE | порядок у файлі | запис = |
|---|---|---|---|
| Power Dolls 2 | `BRIEFING`, `STARTUP`, `PD2SHELL`, `TACTICS`, ... | **B, R, G** | `(byte[3i+1], byte[3i+2], byte[3i+0])` |
| Power Dolls 1 | `PREMIUM.EXE`, `STARTUP.EXE` | **G, R, B** | `(byte[3i+1], byte[3i+0], byte[3i+2])` |

Доказ: із 20 кадрів, знятих із DOSBox-X разом із палітрою (кожен
`out/vram/pd1/*/palette.pal` — це справжній `PC98 DACPAL` емулятора, надрукований
як R,G,B), 11 збігаються з таблицею в EXE PD1 — і **всі** вони збігаються в
порядку `G,R,B`, і жоден — у `B,R,G`. Читання таблиць PD1 «по-PD2» робить блонд
`CHARA04.GCP` маджентовим, а синю уніформу — зеленою.

Інваріант, який робить це перевірюваним без знімка: `PREMIUM.EXE 0xEDF1` і
`STARTUP.EXE 0x9311` у PD2 — це **ті самі 16 кольорів із переставленими першим і
третім байтами**, тож інструментам `pd2pal.py` потрібен порядок для кожної гри.
`tools/verify.py --pd1 DIR` це й перевіряє.

Передається третім полем специфікації:

```
python pd2pal.py --exe    "power dolls 1/_unpacked/PREMIUM.EXE:0xEDF1:G,R,B" -o out/artwork.pal
python pd2gcp.py --gcp    CHARA04.GCP out --pal-exe "PREMIUM.EXE:0xEDF1:G,R,B"
python pd2extract.py --pck FACE.PCK out --pal-exe "BRIEFING.EXE:0x234C6"   # для PD2 типово B,R,G
```

Список порядків — `pd2pal.EXE_ORDERS`; голий `FILE.EXE:0xOFFSET` далі
використовує типовий порядок рутини (`B,R,G`) — саме такий потрібен усім
таблицям Power Dolls 2.

### Формат пакованої таблиці — 32 байти

```
byte[2i]   = (index << 4) | ЗЕЛЕНИЙ
byte[2i+1] =  ЧЕРВОНИЙ << 4 | СИНІЙ
```

Приклад: дефолтна шкала → `00 00 | 0f 10 | f0 20 | ff 30 | 00 4f | …`
(`palette_to_packed` у `pd2pal.py` відтворює 32 байти всіх 26 файлів `.GCP`
байт-у-байт).

## 2. Де ця таблиця реально лежить

| джерело | перевірено | результат |
|---|---|---|
| **усі 26 `.GCP`, зсув `0xB`** | 26/26 валідні | 24 — дефолтна палітра PC-98; **`HARDY.GCP` і `KOGADO.GCP` — кастомні** |
| записи `CHARA.PCK`, зсув `0xB` | 27 записів | усі дефолтні |

Раніше ці 32 байти вважали «сталим прологом стисненого потоку» — насправді це
палітра, і саме тому вона однакова в більшості `.GCP`.

```
$ python pd2pal.py --list ..\hdi\PD2D      # усі палітри в записах
$ python pd2pal.py --gcp ..\hdi\PD2D\HARDY.GCP
000 dfb be9 9d6 683 76c ddd bbb 777 555 bfb 7d8 5b6 efb cf7 fff
$ python pd2pal.py --gcp ..\hdi\PD2D\KOGADO.GCP
000 aac eeb 0e0 996 664 429 ddd aaa 666 444 f8c c08 843 632 fff
```

Дефолтна палітра (з 24 `.GCP`) — це також фолбек `pd2extract.py`, коли не задано
жодного `--pal*`; див. попередження на початку файлу:

```
індекс :  R G B
  0    :  0 0 0     чорний
  1    :  0 0 f     синій
  2    :  0 f 0     зелений
  3    :  0 f f     блакитний
  4    :  f 0 0     червоний
  5    :  f 0 f     малиновий
  6    :  f f 0     жовтий
  7    :  f f f     білий
  8    :  7 7 7     сірий
  9    :  0 0 a     тьмяний синій
 10    :  0 a 0     тьмяний зелений
 11    :  0 a a     тьмяний блакитний
 12    :  a 0 0     тьмяний червоний
 13    :  a 0 a     тьмяний малиновий
 14    :  a a 0     тьмяний жовтий
 15    :  a a a     тьмяний сірий
```

## 3. Де палітри НЕМАЄ — перевірено вичерпно

> **Виправлено 2026-10-11.** Висновок нижче хибний як загальне твердження, і
> причина повчальна: таблиці зберігаються з порядком каналів **(B, R, G)** — це
> *циклічна ротація*, якої перестановки `rgb`/`grb`/`bgr` не дають ніколи, — а
> 16 еталонних кольорів зі скріншота були прив'язані до **неправильних індексів**
> (той самий набір кольорів, інші номери записів). З урахуванням ротації та
> драбини фейду живі палітри збігаються з таблицями у файлах **16/16**: див.
> [`PALETTE_TABLES.md`](PALETTE_TABLES.uk.md) і `tools/pal_tables.py`. Рядки
> нижче лишаються чинними тільки для контейнерів і save-state.

| гіпотеза | як перевіряли | результат |
|---|---|---|
| у записах `.ASK`/`.PCK` | дизасемблер: декодер не торкається портів палітри | **немає** |
| «48 байтів палітри за зсувом 12» | це стиснений потік — доведено кодом і тим, що байти однакові в різних зображень | **не палітра** |
| десь у shipped-даних як таблиця | усі файли **сирі та розпаковані** (обидва контейнери); 32-байтовий packed-формат у всіх 4 розкладках ніблів і з індексом у будь-якій позиції; 48-байтові RGB/GRB/BGR-таблиці; значення як `0..15` і як `n*17`; строге двобічне зіставлення проти 16 кольорів зі справжнього скріншота | **0 збігів** — але збігів і не могло бути: [див. виправлення](PALETTE_TABLES.uk.md) |
| у save-state DOSBox-X | секції `Vga`, `Render`, `Pic`, `Mixer`, `CPU`, `Memory`; різні ширини елемента (2/3/4 байти) і розкладки ніблів, те саме зіставлення | **немає** — палітра PC-98 як апаратний стан не серіалізується |

**Висновок (застарілий).** Палітра художніх екранів збирається в пам'яті під час
виконання **з таблиць, які гра постачає у своїх же EXE** (48 байтів на палітру,
порядок каналів B,R,G, банки з кроком `0x60`/`0xC0`), і передається рутину
запису палітри за образом `0x10A59` у `BRIEFING.EXE`. Тобто вона **є** у файлах і
витягується без емулятора — див. [`PALETTE_TABLES.md`](PALETTE_TABLES.uk.md).
Дамп з емулятора тепер потрібен лише щоб дізнатися, **яку саме** таблицю
використовує конкретний екран.

## 4. Як дістати палітру конкретного екрана

### Варіант A — `.pal` від DOSBox-X (найпростіший)

1. У DOSBox-X **Ctrl+F5** («Save screenshot»).
2. У теці `capture/` з'являться `<ім'я>.png` **і `<ім'я>.pal`**.
3. Далі:

```powershell
python pd2extract.py --all ..\hdi\PD2D out\png --pal capture\game.pal
```

> Скріншот, зроблений засобами Windows, `.pal` не має — це має бути саме
> Ctrl+F5 у DOSBox-X.

### Варіант B — вивести зі скріншота + GVRAM

Потрібні **нескайльований** Ctrl+F5 PNG (рівно 640×400) і save-state з **того
самого** екрана. Інструмент зіставить індексну картинку з GVRAM і виведе
палітру:

```powershell
python pd2pal.py --shot capture\game.png --vram dump\Vga.bin -o out\derived.pal
```

У виводі буде `confidence`:
* `≈1.0` — екран збігається, палітра правильна;
* `<0.9` — скріншот і save-state зняті з різних екранів; тоді треба
  підправити масштаб/зсув (`--sx --sy --ox --oy`) або взяти інший save-state.

`Vga.bin` дістається з `.sav` (це ZIP) — розпакувати запис `Vga`; маппінг GVRAM:
`base = 0x07C000`, крок між площинами `0x10000`, кожна площина 400×80 байтів.
Готовий рендер: `python tools\render_vram.py dump\Vga.bin out\screen.png`.

### Варіант C — своя палітра вручну

`--pal` приймає будь-який із форматів: JASC-PAL, сирі 768 байтів
(256×RGB), 48 байтів (16×RGB, значення 0–15), або текст із 16 рядків `R G B`.

```powershell
python pd2pal.py --default -o out\pc98default.pal      # JASC-PAL
python pd2pal.py --default --fmt nibbles -o out\d.nib  # 48 сирих байтів
```

### Варіант D — застосувати евристику в `pd2extract.py`

Під час рекурсивного або одиночного витягування `--palette auto` сканує
розпаковану теку гри на чотири відомі палітри екранів з EXE (за відомою адресою
або сигнатурою вмісту, тож знаходить і таблиці зі зміщеними адресами у Dash) й
використовує підказку з назви кожного джерела `.PCK`/`.ASK`:

```powershell
python pd2extract.py --all ..\hdi\PD2D out\png --palette auto
python pd2extract.py --pck ..\hdi\PD2D\FACE.PCK out\face --palette auto
```

Щоб зафіксувати власну відповідність, створи JSON-об'єкт із назвою джерела
(базове ім'я без розширення або повне ім'я файла) та шляхом до `.pal`:

```json
{
  "M_CLR": "out/palettes/REPORT.EXE_0138b7.pal"
}
```

Шлях до палітри може бути абсолютним або відносним до теки JSON-файла. Потім
передай файл мапи під час витягування; власний запис має пріоритет над
вбудованою підказкою `auto`:

```powershell
python pd2extract.py --all ..\hdi\PD2D out\png --palette auto --palette-map palette-map.json
```

Зіставлення назв нечутливе до регістру. Наприклад, ключ `M_CLR` спрацює для
`M_CLR.PCK`, а `M_CLR.PCK` можна використати, якщо потрібне точне ім'я джерела.

Якщо EXE лежать окремо, передай їхню теку через `--palette-dir DIR`. Назва на
кшталт `FACE.PCK` обирає відому художню палітру, а `DATAU.PCK` чи
`MISSONHD.PCK` — палітру геймплею. Для назв без розпізнаної ролі використовується
стандартна шкала PC-98. Палітра не виводиться зі значень пікселів і режим не
визначає екран невідомого файла. Переглянути альтернативи можна через
`python pd2pal.py --suggest ..\hdi\PD2D --for FILE.ASK`.

Щоб порівняти файл з усіма збереженими `.pal`-кандидатами, запусти:

```powershell
python pd2pal_sweep.py ..\hdi\PD2D\FACE.PCK out\palettes out\face-sweep
```

Скрипт рекурсивно шукає палітри й створює окрему підтеку для кожної, щоб
відрендерені варіанти можна було порівняти.

## 5. Що можна зробити вже зараз

* **Кольори як у грі для чотирьох зіставлених екранів:** передайте таблицю з
  таблиці на початку цього файлу (`--pal-exe`). Для `FACE.PCK`, художніх екранів
  спорядження/брифінгу, оболонки й екрана запуску це все, що потрібно.
* **Евристичний список кандидатів для файла:**
  `python pd2pal.py --suggest ..\hdi\PD2D --for FACE.PCK` сканує таблиці EXE
  і впорядковує кандидатів за ключовими словами в назві та відомими ролями
  екранів. Кожен рядок містить джерело і зсув для `--pal-exe`. Це лише список
  підказок, не підтверджене зіставлення палітри з файлом: палітра належить
  екрану, а не архіву.
* **Витягнути всі таблиці й вибирати з них:**
  `python tools\pal_tables.py --dump out\pal\tables --data ..\hdi\PD2D` пише один
  JASC `.pal` на кожну знайдену таблицю (44 під `PD2D`; 127 таблиць / 59 різних
  палітр по shipped-даних HDI+FDI) з іменами `<EXE>_<offset>.pal`.
* **Для екрана, який ще не зіставлено:** зніміть його в DOSBox-X (Ctrl+F5 дає
  `.png` + `.pal`) і використайте сайдкар, або знайдіть таблицю за знімком через
  `tools/pal_tables.py --find capture\game_analog.rgb` — і далі `--pal-exe` для
  всього, що з цього екрана.
* **`.GCP` — не растр, але він рендериться**: `pd2gcp.py` декодує display-list
  ([`DISPLAYLIST.md`](DISPLAYLIST.uk.md)). `.GCP` у PD1 не мають палітри взагалі,
  тож завжди потребують `--pal`/`--pal-exe`; `.GCP` у PD2 її несуть (стандартна
  гама в 24 з 26), а портрети `CHARA.PCK` малюються спільною палітрою малюнків, а
  не власною таблицею.
* **Коли ніщо інше не працює — перебирайте.** `pd2sweep.py --data DIR -o out/sweep`
  рендерить кожну картинку в дереві кожною знайденою палітрою й пише по одному
  підписаному контактному аркушу на картинку (`palettes/index.txt` зіставляє
  номери клітинок із джерелами палітр). `--orders all` додатково пробує п'ять
  інших перестановок каналів для кожної 48-байтової таблиці.
* **Геометрія завжди правильна.** Рендер, який «виглядає не так», — це
  невідповідність палітри, а не помилка декодування — [`PITFALLS.md`](PITFALLS.uk.md) §12.
