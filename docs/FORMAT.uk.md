# Формат графіки Power Dolls 2 (PC-98) — повний розбір

Документ самодостатній: його можна читати «з нуля», без контексту.
Усе нижче або **перевірено на байтах**, або явно позначено як неперевірене.

Джерело істини — дизасемблер. Головні адреси наведено в образах EXE
(файловий зсув = образ + `hdrsize*16`) для `CONVERT.EXE` версії з HDI.

---

## 1. Термінологія

| термін | значення |
|---|---|
| **образ (image)** | вміст EXE після MZ-заголовка: `file[hdrsize*16 : hdrsize*16 + (pages-1)*512 + lastpage - hdrsize*16]` |
| **потік** | стиснені дані, які читає кодек |
| **запис** | один блок всередині архіву `.PCK` |
| **GVRAM** | відеопам'ять PC-98: `B=0xA8000`, `R=0xB0000`, `G=0xB8000`, `E=0xE0000`, рядковий крок 80 байтів |

---

## 2. Контейнери

Форматів рівно **три**, і всі вони використовують **один і той самий кодек**.

### 2.1 `.ASK` — одиночна картинка

```
offset  0  u32 decoded_size        # == width * height / 2
offset  4  u16 x                   # екранна координата X, у пікселях
offset  6  u16 y                   # екранна координата Y
offset  8  u16 width               # кратна 8
offset 10  u16 height
offset 12  ... LZSS-потік ...
```

Лоадер (`CONVERT.EXE` образ `0x539C`, виклик `lcall 0x539, 0xc`) відкриває
файл, **читає та відкидає перші 4 байти**
(`fread(&tmp, 4, 1, fp)`), після чого викликач читає 4 рази по 2 байти — разом
12 байтів. Далі кодек читає з того самого `FILE*`. Отже **потік починається з
зсуву 12**.

`.ASK` — це не скрипт. Дванадцять із тринадцяти `.ASK` у грі мають цей
заголовок і є картинками:

| файл | розмір | що це |
|---|---|---|
| `GAMEOVER.ASK` | 640×400 | екран «GAME OVER» |
| `SELMA.ASK`, `MAND.ASK`, `M_FAIL.ASK`, `SINGLE.ASK` | 640×400 | повноекранні картинки |
| `OP_AS0.ASK` | 352×395 | кадр |
| `ST07`…`ST12.ASK` | 192×66 | плитки (y = 0, 66, 132, 198, 330) |
| `GOONPD2.ASK` | 272×14 (x=184, y=186) | банер |
| `S_ROLL.ASK` | — | **виняток:** це «сирий блок», див. §2.3 |

### 2.2 `.PCK` — архів

```
u32 offset_table_end                     # довжина таблиці (кратна 8)
(offset_table_end / 8) × { u32 data_offset; u32 file_size }
дані починаються з offset_table_end + 4
запис i = file[offset_table_end + 4 + data_offset : + file_size]
```

Перевірено на всіх 39 архівах: `data_offset` наростає від нуля, а останній
запис закінчується рівно на EOF.

Записи бувають **двох родів**, і розрізняються вони перевіркою

```python
decoded_size == width * height / 2      # і width % 8 == 0
```

| рід | приклади | що це |
|---|---|---|
| **картинки** | `FACE`, `DFACE`, `ARMS`, `EVKAO`, `WEAPON`, `HIDAN`, `DATAU`, `EVENT`, `M_CLR`, `SMAP`, `MMAP`, `SCORE_N` (27/38), `SCORE_P`, `STAFF_G`, `STAFF_P`, `BLANC`, `OP_AS` (1/29) | той самий формат, що `.ASK` |
| **display-list'и** | `CHARA`, `ANIME`, `MES`, `WMES`, `INIT`, `NAMES`, `MOJI`, `NPC`, `MAP_CHG`, `MISSON*D`, `MUNIT`, `TUNIT`, `SCN_MIS`, `YAOUPD1` | команди для GDC (той самий стиль, що `.GCP`) |

Записи другого роду **не є растрами** — намагатися їх «декодувати як картинку»
марно.

### 2.3 «Сирий блок»: `u32` + LZSS зі зсуву 4

```
offset 0  u32 decoded_size
offset 4  ... LZSS-потік ...
```

Таким зроблені **усі `.SLD`** (`HUNIT`, `KIRI`, `MES0`, `RMES`, `OP_EYES`,
`OP_WAI_A/B/C`) і **`S_ROLL.ASK`** (640×320, `decoded_size = 102400`).

Як відрізнити від §2.1: у правильного варіанта потік споживається **рівно до
останнього байта** (`used == file_size - start`, розбіжність ≤ 1 байт — хвіст
бітового буфера). Варіант із заголовком на 12 байтів для `S_ROLL.ASK` дає
102262 байти й упирається в кінець потоку — тобто він неправильний.

### 2.4 `.GCP` — НЕ картинка

`.GCP` — це **список команд для апаратного GDC** PC-98. Обробник
`CONVERT.EXE` образ `0x5CE2`:

* відкриває файл, читає його цілком у буфер;
* `mov dx,0x7c / out dx,al` та `mov dx,0x7e / out dx,al` — пише напряму в порти
  GDC;
* бере байти за зсувами `0,1,2,3` і (за потреби) `8,9,10`;
* адресу цілі обчислює як `y*0x50 + x/8` (крок VRAM = 80).

Заголовок `.GCP` (12 байтів) + **32-байтова палітра за зсувом `0xB`**
(див. [`PALETTE.md`](PALETTE.uk.md)) + команди зі зсуву `0x2B`. Ця таблиця — ще й
фолбек-палітра витягувача, і це **не** палітра, яку гра використовує для своїх
художніх екранів: рендер без `--pal`/`--pal-exe` має неправильні кольори, див.
розділ «Читати першим» у [`PALETTE.md`](PALETTE.uk.md).

Картинка не несе ту палітру, з якою її показують: більшість записів-зображень
`.ASK`/`.PCK` не мають палітри взагалі (`FACE.PCK`: 0 з 38), а 32-байтова
таблиця, яка в частини з них таки є за зсувом `0xB`, — це дефолтна шкала; див.
§2 у [`PALETTE.md`](PALETTE.uk.md) і
[`PALETTE_TABLES.md`](PALETTE_TABLES.uk.md).

Те саме стосується записів-«display-list'ів» у `.PCK` — вони мають ідентичну
структуру заголовка (`struct[8] == 0x22`).

## 3. Кодек

Відновлено з `CONVERT.EXE`, образ **`0x54E6`**, точка входу — `lcall 0x539, 0x156`.
Сигнатура C: `decode(far *handle, byte *out, int len)`.

### 3.1 Структура стану

```
+0x0000  u16 match_base    абсолютний індекс у кільці, звідки копіювати
+0x0002  u16 match_len     довжина копіювання
+0x0004  u16 wpos          індекс запису в кільце, маскується & 0xFFF
+0x0006  u16 state         0/1 = межа токена, 2 = продовження копіювання
+0x0008  u16 match_i       індекс продовження всередині копіювання
+0x000A  u16 bitbuf        бітовий буфер
+0x000C  u8  ring[4096]    кільцевий буфер
+0x101D  FILE *fp
```

Ініціалізація (образ `0x539C` / `0x5459`, `enter 8,0`, `malloc(0x101F)`):

```
ring[0 .. 0xFED] = 0        // 4078 байтів
wpos   = 0xFEE              // 4078
bitbuf = 0
state  = 0
перші 4 байти файлу читаються й відкидаються
```

Зверніть увагу: кільце — 4096 байтів (маска `0xFFF`), але обнуляються перші
4078, і покажчик запису стартує з 4078. Це не помилка читання — саме так у
коді (`cmp word ptr es:[bx], 0xFEE` / `mov word ptr es:[bx+4], 0xFEE`).

### 3.2 Читання бітів

```c
bitbuf >>= 1;
if ((bitbuf & 0x100) == 0)
        bitbuf = 0xFF00 | fgetc(fp);      /* 8 бітів на байт, LSB-first */
bit = bitbuf & 1;
```

Сентинел `0x100` означає «в буфері ще є невикористані біти». Після
`bitbuf = 0xFF00 | c` біт 8 встановлено, і він скидається рівно через 8 зсувів.
Отже порядок бітів — **молодший уперед**.

### 3.3 Токени

```c
if (bit == 1) {                     /* літерал */
        b = fgetc(fp);
        ring[wpos] = b;
        wpos = (wpos + 1) & 0xFFF;
        *out++ = b;
} else {                            /* копіювання: два байти c1, c2 */
        c1 = fgetc(fp);
        c2 = fgetc(fp);
        base  = c1 | ((c2 & 0xF0) << 4);   /* 12-бітний АБСОЛЮТНИЙ індекс */
        count = (c2 & 0x0F) + 3;           /* див. пастку 2 нижче */
        for (i = 0; i < count; i++) {
                b = ring[(base + i) & 0xFFF];
                ring[wpos] = b;
                wpos = (wpos + 1) & 0xFFF;
                *out++ = b;
        }
}
```

### 3.4 Дві пастки, через які не працює «звичайний» LZSS

**Пастка 1 — зміщення абсолютне, а не відносне.**
`base` — це **індекс у кільці**, а не відстань назад від `wpos`. У
«канонічному» LZSS читають `ring[(wpos - offset) & mask]`. Тут — `ring[(base + i) & 0xFFF]`.
Кодер, відповідно, запам'ятовує абсолютну позицію входження.

**Пастка 2 — довжина на одиницю більша, ніж каже `add ax,2`.**
В асемблері стоїть `add ax, 2`, але цикл копіювання перевіряється як

```
0x56EF  mov ax, es:[bx+2]      ; match_len
0x56F2  cmp ax, word ptr [bp-4]; cmp len, i
0x56F5  jge 0x569B             ; if len >= i -> copy
```

тобто тіло виконується для `i = 0 … len` **включно** — на один раз більше.
Реальна довжина = `(c2 & 0x0F) + 3`.

Перевірка цього: перебір параметрів, у якому довжина `+3`, дає рівно
`decoded_size` на всіх чотирьох тестових записах, а `+2` — ні.

### 3.5 Вивід: 4 біти на піксель, інтерлівінг

Вихід — не «4 послідовні площини», а **по 4 байти на кожну групу з 8 пікселів**:

```
для кожного рядка y = 0 .. height-1:
  для кожного байт-стовпця xb = 0 .. width/8 - 1:
     байт 0 -> площина B  (біт кольору 0)
     байт 1 -> площина R  (біт кольору 1)
     байт 2 -> площина G  (біт кольору 2)
     байт 3 -> площина E  (біт кольору 3)
```

Загальний розмір `width/8 * height * 4 == width*height/2` ✔

**Порядок доведено кодом вивантаження в GVRAM** (`CONVERT.EXE` образ `0x5B1F`):

```
0x5B23  mov ax,0xA800        ; B-площина
0x5B2B  mov si,0x8AEC        ; staging-буфер, куди покладено байт 0
        rep movsw / movsb    ; -> 0xA8000 + зсув

0x5B42  add di,0x8000        ; R-площина (0xB0000)
0x5B46  mov si,0x8A9C        ; байт 1

0x5B53  mov ax,0xB800        ; G-площина
0x5B5A  mov si,0x8A4C        ; байт 2

0x5B67  mov ax,0xE000        ; E-площина
0x5B6E  mov si,0x89FC        ; байт 3

0x5B81  add word ptr [bp-0x38], 0x50   ; рядковий крок VRAM = 80
```

Тобто послідовність байтів у потоці — `B, R, G, E`, або біти кольору `0,1,2,3`.

**Біти в байті — старший уперед** (лівий піксель = біт 7). Реверс бітів
(таблиця 256 байтів, яка будується за образом `0x57AD` через `shr/rcl`) у
звичайному режимі **не застосовується**: він потрібен лише коли 5-й аргумент
`DrawPicture` ненульовий (перевірка на образі `0x592C`). У тому ж режимі
площинні рядки ще й байто-свапаються хелпером `0x5C2C` (`mov al,[si] / mov
al,[di] / mov [si],…` — обмін двох байтів).

### 3.6 Чому в пам'яті немає проміжного буфера

`DrawPicture` (образ `0x5723`) викликає кодек **по 4 байти за раз** і одразу
розкладає їх по чотирьох площинних staging-буферах (по 80 байтів, DGROUP
`0x89FC/0x8A4C/0x8A9C/0x8AEC`). Проміжного 4608-байтового буфера не існує —
саме тому попередні пошуки «виходу декодера в RAM» нічого не знаходили.

## 4. Перевірка правильності

Кодек вважається правильним із таких підстав:

1. **Візуально.** `GAMEOVER.ASK` дає цілком читабельний екран «GAME OVER» на
   тлі візерунка «POWER DoLLS 2». `M_CLR.PCK` — повні екрани
   «MISSION COMPLETE / Congratulations!» з портретами й підписами
   (Alice Knox, Selma Shaldon, …). `WEAPON`/`ARMS`/`FACE`/`DFACE`/`EVKAO` —
   чисті зображення. Випадковий потік байтів такого дати не може.
2. **Статистика.** Вихід має 20–78 % нульових байтів і однорідні ділянки
   завдовжки до **2176 байтів**. Для випадкових даних — 0.3 % і максимум 2.
3. **Споживання потоку.** Кодек з'їдає весь потік (залишається рівно 1 байт —
   хвіст бітового буфера) на **всіх 360** зображеннях.
4. **Ідентичність коду.** Декодер у `TACTICS.EXE` та `BRIEFING.EXE` збігається
   з `CONVERT.EXE` байт-у-байт, крім 12–16 байтів — і всі вони всередині
   імедіатів `lcall` на рантайм (`fgetc`, `exit`). Тобто це один статично
   злінкований бібліотечний рутин.

### Що **не** є критерієм

«Декодер видав рівно `decoded_size` байтів» — **не доказ**. LZSS
само-доповнюється: він може видати будь-яку замовлену довжину з порожнього
кільця. Перевірено: **360/360 записів «проходять» такий тест для 40 різних
наборів параметрів**, включно з неправильними. Єдині надійні критерії —
візуальна читабельність і точний збіг із GVRAM.

* `FACE.PCK` у **флопі-** та **HDI-релізі різні**: 36 записів проти 38, і
  запис 0 відрізняється. Ніколи не змішувати ці два релізи.

## 6. Що залишилось невідомим

* **Компресор.** Пакувальник є в `CONVERT.EXE` (він володіє обома
  розширеннями `.pck`/`.gcp`, рядками `rb`/`wb`, `File is not found <%s>`).
  Шукати поруч із декодером за образом `0x54E6`.
* **`.GCP`/display-list'и.** Семантику команд не розібрано (обробник
  `0x5CE2`). Потрібно лише якщо треба відтворювати ці екрани без гри.
* **Точні палітри художніх екранів** — вирішено: таблиці постачаються в самих
  EXE (48 байтів, порядок каналів B,R,G) —
  [`PALETTE_TABLES.md`](PALETTE_TABLES.uk.md), `tools/pal_tables.py` або
  `pd2extract.py --pal-exe "FILE.EXE:0xOFFSET"`. Яка таблиця якому екрану
  належить — зіставлено лише для чотирьох екранів, а дефолтна `.GCP`-шкала
  витягувача **не** є палітрою гри ([`PALETTE.md`](PALETTE.uk.md), «Читати
  першим»).
